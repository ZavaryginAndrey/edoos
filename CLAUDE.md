# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Health Coach Agent: a Next.js 16 (App Router) web app wrapping two LLM agents built on the OpenAI Agents SDK (`@openai/agents`), running against DeepSeek through its OpenAI-compatible Chat Completions API. All prompts, UI copy, logs and error messages are in Russian — keep new user-facing text in Russian.

## Commands

```bash
npm install
npm run dev          # http://localhost:3000 — must be run from the repo root (see data/ paths below)
npm run build
npx tsc --noEmit     # typecheck; there is no lint or test setup
npm run replay runs/run-XXX.json   # re-run a traced task through the current harness, print old vs new
npm run eval         # run evals/cases/*.json sequentially, PASS/FAIL table (real DeepSeek calls)
npm run mcp:inspect  # spawn every enabled MCP server from the config over stdio, print tools (as the model sees them, with config visibility) and resources (no LLM)
npm run ingest       # knowledge/*.md → chunks by ## → OpenAI embeddings → Supabase knowledge_chunks (truncate + insert in one transaction; idempotent)
```

Required `.env` in the repo root: `DEEPSEEK_API_KEY`. Optional: `DEEPSEEK_BASE_URL` (default `https://api.deepseek.com`), `DEEPSEEK_MODEL` (default `deepseek-v4-flash`), `NOTION_TOKEN` (Notion internal integration token; enables the notion MCP server), `SUPABASE_DB_URL` (Postgres connection string; RAG), `EMBEDDING_API_KEY`, `EMBEDDING_BASE_URL` (default `https://api.openai.com/v1`), `EMBEDDING_MODEL` (default `text-embedding-3-small`, must be 1536-dim — DeepSeek has no embeddings API). Without the RAG vars the app still runs; `searchKnowledge` returns an error string to the model. External MCP servers run via `npx -y <pinned package>`, so the first run needs network.

There is no user-facing CLI by design (the old `index.ts` was removed): users run the agents from the chat UI (`POST /api/chat`, streamed) or via `POST /api/agent/run` with `{ task }` (curl, one JSON response). `tsx` exists only for the dev scripts in `scripts/` (`replay.ts`, `eval.ts`, `mcp-inspect.ts`, `ingest.ts`), thin CLI wrappers over `src/dev/` that load `.env` via `--env-file-if-exists`. Round-by-round logs go to the `next dev` server console.

## Architecture

Request flow: `app/page.tsx` (client chat, `useChat`) → `app/api/chat/route.ts` (streamed, see "Chat streaming" below; curl uses `app/api/agent/run/route.ts`, evals call the harness directly) → `runHealthAgent(task, { maxRounds = 3, minRounds = 1, promptVersions = ACTIVE_PROMPTS, onEvent? })` in `src/harness/runHealthAgent.ts` → returns `{ plan, review: { verdict, score, issues }, rounds: RoundState[], finalScore, improved, promptVersions, model, toolCalls, retrievals, actions, durationMs }` (`toolCalls` = model-facing names of the tools the coach actually executed, in order, across all rounds and the save step: MCP tools as `mcp_<server>__<tool>`, local tools unprefixed; calls to tools the agent didn't have are logged, not listed. `retrievals` = `{ query, chunks: [{ file, heading, similarity }], error? }[]`, one per `searchKnowledge` call in call order (the UI pairs the n-th `searchKnowledge` in `toolCalls` with the n-th retrieval). `actions` = enabled `button` servers, `{ server, label }[]`, rendered as buttons under an approved plan).

Button actions: `POST /api/agent/action { server, plan }` → `runServerAction()` in `src/harness/runServerAction.ts`. It only accepts a `button` server from the config, spawns `markdown-health` + that server, rejects the plan unless it equals `plans://latest` (the last approved plan), then runs the coach with only that server's MCP tools, `{ approvedPlan }` in context and `button.task` + plan as input (`maxTurns: 8`). Returns `{ server, output, toolCalls, durationMs }`; no trace. Shared coach plumbing (`configureDeepSeek`, `runCoach`, `todayLine`, `normalizePlan`) lives in `src/harness/coachRun.ts`.

`src/harness/` is split by responsibility: `runHealthAgent.ts` (orchestrator only), `validateReview.ts` (zod `ReviewSchema`, `safeParseReview`, one-retry `validateReview`), `rounds.ts` (`RoundState { round, plan, review }`, `RoundHistory`, round log line), `score.ts` (`finalScore` = score of the last `approve`, else null; `improved` = last round score > first), `promptVersions.ts` (`ACTIVE_PROMPTS` + loading `prompts/<name>.<version>.md`). `traceRun.ts` (`buildTrace` + `traceRun`: every completed run — pre-check stop included — writes `runs/run-<timestamp>.json` from `finish()`; write errors are logged, never thrown; runs that throw leave no trace). Persisted: `data/output.md`, `data/shopping.md`, `plans/*.md` (written by the filesystem MCP; `plans/.gitkeep` must exist or that server won't start) and `runs/*.json` (gitignored except `runs/run-example.json` and `plans/.gitkeep`). Eval cases are `evals/cases/*.json` (`{ name, task, expect: { verdict, minScore?, toolCalls? } }`; `toolCalls` = tool names that must appear in `result.toolCalls`); normal-case tasks must avoid the pre-check regex words (`боль(?!ш)` is deliberately not triggered by «больше»/«большой»).

The orchestration loop in `runHealthAgent` is explicit — the two agents never talk to each other directly and there are no SDK handoffs. Only the coach has tools (see Tools and MCP below); the reviewer has none:

1. **Pre-check** — `reviewTaskSafety()` (`src/agents/safetyReviewer.ts`) is a regex filter over the raw task (medications, dosages, symptoms, pressure, heart, sugar, pregnancy, injury…). A match short-circuits with `needs_human_professional` before any LLM call or API-key check; it is recorded as round 1 with an empty plan.
2. **Up to `maxRounds` (default 3) rounds**: the coach (`src/agents/healthCoach.ts`) gets only a «Сегодня: <date>» line and the task, fetches what it needs via tools and writes a Markdown plan (`maxTurns: 10` — each tool round-trip is a turn; v5 adds knowledge searches); the reviewer gets only the task + plan text and returns JSON validated by `validateReview()` against the zod `ReviewSchema` (`maxTurns: 1`). Invalid JSON gets exactly one retry with a corrective suffix, then throws.
3. Verdict handling: `approve` before `minRounds` → loop continues (issues go to the coach, verdict is recorded as-is); `approve` → a save step re-runs the coach (`maxTurns: 6`) with `{ approvedPlan }` in the run context and the original task in the input, so it calls `save_health_plan` and, if the user asked, writes `plans/<date>.md` via filesystem (both are `afterApprove` tools); the harness then reads `plans://latest` and, if it doesn't match the approved plan (tool not called or text altered), calls `save_health_plan` itself through the same MCP server, then the plan is returned; `needs_human_professional` → returns with an empty plan; `revise` → the reviewer's `issues` plus the previous plan are appended to the coach prompt for the next round. If all rounds end in `revise`, the last plan is returned but **not** saved.

Agent instructions live in `prompts/healthCoach.<v>.md` and `prompts/safetyReviewer.<v>.md`; the active versions are `ACTIVE_PROMPTS` in `src/harness/promptVersions.ts` (read from `join(process.cwd(), "prompts")` on every request). A new prompt version = a new file + changing that constant; the versions used are returned as `promptVersions`.

### Dev console (`/dev`, dev only)

Replay and eval logic lives in `src/dev/` and is shared by the CLI scripts and the UI: `replay.ts` (`listTraces`, `readTrace`, `parseTrace`, pure `compareTraces`, `replayTrace`), `evals.ts` (`listEvalCases`, `readEvalCase`, pure `checkEval`/`describeExpect`, `runEvalCase` — agent errors become a failed row, not a throw), `devOnly.ts` (`devEnabled()`, 404/500 helpers). `runId` and case ids are validated by regex against path traversal. `app/dev/page.tsx` is a server component (`notFound()` in production, `force-dynamic`) that reads the lists and renders the client `app/dev/dev-console.tsx`; runs go through `POST /api/dev/eval { id }` and `POST /api/dev/replay { runId }` (404 in production, 400 on bad ids before any LLM call). The console allows one run at a time (`runHealthAgent` configures the DeepSeek client globally), runs "all evals" as sequential per-case requests, and calls `router.refresh()` after each run so the new trace shows up. `src/dev/*` reads files — client code imports only its *types*.

Test mode (dev only): `/api/agent/run` and `/api/chat` accept `minRounds` and `prompts: { coach?, reviewer? }` (shared `parseTestOptions` in `app/api/agent/test-options.ts`; 400 in production); the chat UI reads them from the URL, e.g. `/?coach=test-revise&reviewer=test-revise` runs `prompts/*.test-revise.md`, which force a revise → approve cycle.

### Chat streaming (`src/chat/`, `app/api/chat`)

- `src/harness/events.ts` — `HealthAgentEvent` (`coach_start/end {round}`, `tool_start/end {step, callId, name, args}`, `review_start/end {round, review, precheck}`, `save_start/end`), `safeEmit` (a throwing subscriber is logged, never breaks the run) and `emitToolEvents` (Agents SDK `agent_tool_start/end` hooks on the coach *instance*, not the global runner; they fire in plain `run()`, and calls to missing tools produce none — same as `toolCalls`). `runHealthAgent` only inserts `emit(...)` calls; without `onEvent` nothing subscribes and behavior is unchanged (evals, `/api/agent/run`, replay). The harness's own fallback `save_health_plan` call is not an event.
- `app/api/chat/route.ts` — body `{ task, minRounds?, prompts? }`: the client sends only the last message's text, every message is an independent run (the harness has no dialogue). `createUIMessageStream` (AI SDK `ai@7`): events → `createTimeline` (`src/chat/timeline.ts`) → `data-stage` / `data-tool` parts with stable ids (`r<N>-profile|knowledge|writing|review|revising`, `final`; tool id `<stage id>-<callId>`) that `useChat` reconciles in place. Round 1 tools are grouped by meaning (markdown-health reads → profile, `searchKnowledge` → knowledge, the rest → writing); from round 2 all tools go to `revising`, save-step tools to `final`. After `runHealthAgent` returns, `streamPlan` (`src/chat/streamPlan.ts`) replays the already reviewed plan as `text-delta`s (~3 words / 15 ms; the deltas join back to the exact plan) and `data-result` comes last. Unreviewed text never reaches the client, so `needs_human_professional` shows a card instead of a plan. On an exception `timeline.fail()` marks active rows `error` and `onError` sends the Russian message. If the client disconnects, the run still finishes (plan saved, trace written).
- `src/chat/messages.ts` — `HealthChatMessage = UIMessage<never, { stage, tool, result }>` and the part types; client code imports only these types.

### Tools: local (`src/skills/`) and MCP (`src/mcp/`)

Nothing from `data/` is pasted into prompts. The coach (`src/agents/healthCoach.ts`) gets two kinds of tools that look identical to the model (plain function tools in one list). MCP tools get the server prefix from the SDK (`mcpConfig.includeServerInToolNames`): `mcp_weather__metno_forecast`. The SDK replaces `-` with `_` in both parts (`mcp_markdown_health__save_health_plan`, `mcp_notion__API_post_page`), so server names are kebab-case without `_` and the UI (`parseTool` in `components/agent-result.tsx`) maps `_` back to `-` for the `[source]` badge; local tools (our own app code in `src/skills/`) show as `health-agent`. Prompts must use the prefixed names.

- **Local** — `COACH_TOOLS`, a plain array of `tool()`s from `src/skills/` (zod schema + model-facing Russian description; descriptions are part of the interface — edit with care): `suggestWorkoutTemplate(goal)` → one of 4 hardcoded templates; `generateShoppingList(planMarkdown)` → deterministic dictionary extraction (no LLM) from the plan's `## Питание` section, sums amounts, overwrites `data/shopping.md`. They stay local on purpose, as the contrast to MCP.
- **MCP** — `src/mcp/markdownHealthServer.ts`, our own stdio MCP server on `@modelcontextprotocol/server` (MCP TS SDK v2; `@openai/agents` uses `@modelcontextprotocol/client` v2). Tools: `read_profile`, `read_recent_logs(days)` (last N `## <date>` entries of `data/log.md`, by position: dates have no year), `list_recipes`, `save_health_plan(markdown)` (overwrites `data/output.md`), `append_daily_log(entry)`. Resources: `profile://me`, `logs://recent` (last 7 entries), `recipes://all`, `plans://latest`. The server is data only — no verdicts, scores or validation (those stay in the harness). It runs as `node src/mcp/markdownHealthServer.ts` (Node strips types natively), so it must stay self-contained: no imports from `src/`, no TS syntax that needs compiling; stdout is the protocol, log to stderr only. Data is read from `join(process.cwd(), "data")` of the spawned process.
- **Config** — `src/mcp/servers.config.ts`, `MCP_SERVERS: { name, command, args, env?, enabled, tools?: { allow?, block?, afterApprove?: string[] | "*" }, button?: { label, task } }[]`. Adding a server = adding an entry; the harness must not need changes. Entries: `markdown-health` (ours, `block: append_daily_log`, `afterApprove: save_health_plan`), `filesystem` (`@modelcontextprotocol/server-filesystem`, allowed dirs = `<cwd>/data` and `<cwd>/plans` only, `afterApprove: "*"`), `weather` (`open-meteo-mcp-server`, `allow: ["metno_forecast"]` — MET Norway models; chosen over `@pipeworx/mcp-met-no` whose forecast is ~80k chars with no way to narrow it), `notion` (`@notionhq/notion-mcp-server`, `enabled: Boolean(process.env.NOTION_TOKEN)`, `button` server). Package versions are pinned. `DATA_SERVER = "markdown-health"`.
- **Runtime** — `src/mcp/servers.ts`: `runServerConfigs()` (enabled, no `button`), `buttonServerConfigs()` (enabled, `button`), `connectServers(configs)` (`connectMcpServers` with `dropFailed` + `connectInParallel`: a server that fails to start is dropped with a warning), one generic `configToolFilter` built from `tools`, `readResource`, `LATEST_PLAN_URI`. `afterApprove` tools are visible only when the run context has `approvedPlan`. `cacheToolsList` must stay `false`: the SDK caches the list *after* the filter, which would freeze gated tools as hidden. Child processes get only the MCP client's safe default env plus the entry's `env` — `.env` secrets don't leak into servers.
- Lifecycle: `runHealthAgent` spawns the run servers after the pre-check/API-key/prompt loading and closes them in `finally` before writing the trace; the coach gets them via `mcpServers`. One set of processes per run. If `markdown-health` is disabled or failed, the save check/fallback is skipped with a log line.
- `runCoach` passes `toolNotFoundBehavior: "return_error_to_model"`: prompts mention tools of every server, and a disabled server must not crash the run when the model calls its tool anyway.
- Relative paths in the filesystem server resolve against its *first* allowed dir (`data/`), so prompt v4 tells the coach to take the absolute `plans` path from `list_allowed_directories`.
- The Safety Reviewer must stay side-effect free: no tools, no MCP servers, no data files, only task + plan text.
- `@modelcontextprotocol/node` (HTTP adapter) is in dependencies but unused — network transports are out of scope.

### RAG (`src/rag/`, `knowledge/`)

Simple RAG, no frameworks (no LangChain/LlamaIndex), no reranking/hybrid search/query rewriting: one embedding, one pgvector similarity search.

- `knowledge/*.md` — the knowledge base («что мы умеем»: recipes, nutrition rules, training templates, recovery rules, preference-handling rules). 1 `## ` section = 1 chunk (`src/rag/chunking.ts`; text before the first `##` is dropped; `(file, heading)` is unique). Personal memory (`data/profile.md`, `data/log.md`, `data/recipes.md`) stays in markdown/MCP — do not move it to the DB.
- `src/rag/embeddings.ts` — `embed(texts)` via plain `fetch` to `<EMBEDDING_BASE_URL>/embeddings`, checks dimension = `EMBEDDING_DIMENSIONS` (1536, matches `vector(1536)`). `src/rag/db.ts` — lazy `postgres` client from `SUPABASE_DB_URL` (`prepare: false` for the Supabase pooler, TLS unless localhost, short `idle_timeout` so CLI scripts exit). `src/rag/retriever.ts` — `searchKnowledge(query, topK = 5)`: raw SQL `order by embedding <=> $1::vector limit $2`, `similarity = 1 - distance`.
- Schema: `supabase/migrations/001_knowledge.sql` and the identical `docs/001_create_knowledge_chunks_table.sql` (SQL the user runs lives in `docs/NNN_*.sql`; keep both in sync). Table `knowledge_chunks(id, file, heading, content, embedding vector(1536))`, hnsw `vector_cosine_ops` index, RLS on with no policies. A different embedding dimension = a new migration.
- `scripts/ingest.ts` — embeds everything first, then `truncate … restart identity` + bulk insert in one transaction (idempotent; an API failure leaves the table untouched).
- Tool: `src/skills/knowledge.ts` (`searchKnowledge`, local, first in `COACH_TOOLS`). It pushes a `Retrieval` into `CoachContext.retrievals` synchronously before awaiting (keeps call order for parallel calls); `runCoach` creates that array per run and returns it; `runHealthAgent` accumulates into `result.retrievals` → trace (`RunTrace.retrievals?`, optional for pre-RAG traces) → UI (`<query> → N chunks` row in `ToolCallList`, collapsed; expands to chunk headings + similarity). DB/embedding errors are returned to the model as text and recorded in `retrieval.error`, never thrown.
- Prompt `healthCoach.v5.md` (active): search the knowledge base before writing nutrition/activity/recovery, take dishes only from `searchKnowledge` or `list_recipes`, cite `(база знаний: <file> › <heading>)`.

The DeepSeek client is configured globally by `configureDeepSeek()` (`src/harness/coachRun.ts`) on each `runHealthAgent`/`runServerAction` call (`setTracingDisabled`, `setOpenAIAPI("chat_completions")`, `setDefaultOpenAIClient`).

Per the README, the prompts, pre-check and loop were ported from the earlier V0 version unchanged — treat changes to them as behavior changes, not refactors.

### UI

- `app/page.tsx` is a single client chat component on `useChat` (`@ai-sdk/react`, `DefaultChatTransport` → `/api/chat`). History lives only in `useChat` state (no persistence, one chat); Enter sends, Shift+Enter is a newline; the input is disabled while running; window scroll sticks to the bottom unless the user scrolled up. Messages render via `components/chat/message.tsx` (user bubble; assistant: timeline → plan `Markdown` → verdict/score footer with copy and action buttons, or the «Требуется специалист» card) and `components/chat/timeline.tsx` (`AgentProgress`: a phase stepper Данные → План → Проверка → Сохранение derived from the stages, with round and elapsed time; below it the stages on a vertical line, sorted by round and kind, `final` last. Calls to the same tool inside a stage are one collapsible group with a loader while any call is active and a live "3 из 6" counter; a stage stays expanded while active and collapses when done unless the user toggled it). The `/dev` result cards (`Result`, round history, tool calls, `VERDICTS`, `MAX_ROUNDS`) live in `components/agent-result.tsx`, which also exports the pieces the chat reuses. `MAX_ROUNDS = 3` there duplicates `DEFAULT_MAX_ROUNDS` in `src/harness/runHealthAgent.ts` — keep them in sync. The /dev result card shows duration, prompt versions and a collapsed round history (`components/ui/collapsible.tsx`). The header links to `/dev` only when `NODE_ENV !== "production"`.
- Built with **shadcn/ui** (`components.json`: style `base-nova` on Base UI primitives, `rsc: true`, lucide icons) and **Tailwind CSS v4** (via `@tailwindcss/postcss`, no `tailwind.config`). Add components with `npx shadcn@latest add <name>` — they land in `components/ui/` and are owned code; style with Tailwind utilities and theme tokens rather than new CSS. Base UI composes via the `render` prop (e.g. `<TooltipTrigger render={<Button />}>`), not Radix's `asChild`.
- `app/globals.css` is the shadcn theme: CSS variables on `:root` / `.dark` mapped through `@theme inline`. Beyond the stock tokens it adds `--success` and `--warning` (used for review verdicts) and `--rag` / `--mcp` / `--agent` (tool-call kind: icon + `SourceBadge` pill; `--agent` is teal for `health-agent` so it never reads as the green approve verdict). Keep the neutral palette; color is reserved for status and tool kind.
- Dark mode: `next-themes` (`attribute="class"`, system default) in `components/providers.tsx`, toggle in `components/theme-toggle.tsx`. On the client the theme script gets `type="application/json"` to silence React 19's "script tag in a client component" warning — it has already run from the server HTML.
- `components/markdown.tsx` is a hand-rolled minimal Markdown renderer (headings, lists, tables, paragraphs, bold/italic/code) that renders model output as React text only — intentionally no `dangerouslySetInnerHTML` and no Markdown library. Output is wrapped in `.typeset` from `app/typeset.css` (shadcn/typeset, downloaded from ui.shadcn.com/typeset.css); tables go in `.typeset-scroll` for horizontal scroll on mobile.
- Fonts: Geist and Geist Mono (Latin + Cyrillic subsets) from `next/font/google` in `app/layout.tsx`.
- `InputGroup`'s `has-disabled:*` styles also fire for a disabled button inside it; `app/page.tsx` overrides them so the composer doesn't fade while Run Agent is disabled.
- Import alias `@/*` maps to the repo root (e.g. `@/src/harness/runHealthAgent`).
